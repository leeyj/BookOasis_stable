# 로컬 스캔 중 웹 대시보드 SQLite 락 경합 완화 조치

## 1. 버그 내역 및 증상
- 백그라운드에서 로컬 라이브러리 스캔 작업이 활발히 진행 중일 때, 사용자가 웹 대시보드를 탐색하거나 진척도 변경 등의 작업을 수행하려 하면 브라우저 화면에 DB 접속 에러(`database is locked`)가 노출되는 간헐적 장애 현상 발생.

## 2. 원인 분석
- **초고속 디스크 I/O와 조밀한 DB 쓰기**: 로컬 디스크 스캔은 네트워크 전송 지연이 없기 때문에 파일 탐색 및 파싱이 끝나는 대로 초당 수십~수백 번의 DB 쓰기(`INSERT`/`UPDATE` 및 `conn.commit()`) 요청을 연달아 날림.
- **SQLite Single-Writer 제약**: SQLite3는 WAL 모드가 적용되어 있어도 동시 쓰기(Write)는 오직 단 하나의 스레드만 가능함. 스캐너가 쉬지 않고 쓰기 락을 선점하기 때문에 대시보드 API 스레드의 쓰기 시도(세션 기록, 읽기 로그 기록 등)가 락에 차단되어 타임아웃을 초과하게 됨.
- **제어권 양보 부재**: 벌크 커밋(`conn.commit()`) 이후 바로 다음 루프로 진입하여 다른 비동기 스레드가 끝나는 대로 즉시 DB 쓰기를 지속하므로, 다른 웹 스레드에 DB 접속 기회를 양보(Yield)하지 못함.

## 3. 조치 사항
1. **Micro-Yield (미세 양보 딜레이) 설계 도입 (`tools/scanner/engine.py`)**:
   - `flush_pending_data()` 함수 내에서 DB 벌크 배치 갱신 후 atomic 트랜잭션이 커밋(`conn.commit()`)되는 시점 직후에 **`time.sleep(0.05)` (50ms)** 딜레이를 주입함.
   - 이 미세 딜레이는 스캔 속도 저하를 최소화(10,000권 기준 단 5초 내외 추가)하면서, 대시보드 웹 스레드들이 락을 안전하게 선점하여 웹 인터페이스 조작을 완수할 수 있는 숨통을 틔워 줌.
2. **트랜잭션 세분화 보장**:
   - 개별 스레드 풀 타스크(`process_folder_task`) 내부에서는 DB 작업을 완전히 배제하고 FS I/O만 순수하게 돌리며, 메모리에 축적된 배치 데이터 커밋 시에만 트랜잭션을 매우 짧게 가져가는 기존의 아키텍처적 격리 상태를 확인 및 유지함.

## 4. 해결 확인 및 영향도
- 로컬 스캔 작동 중에도 웹 대시보드 화면이 막힘 없이 부드럽게 렌더링되며, 이어읽기나 책 클릭 시 동시성 에러 없이 정상적으로 구동됨.
- 스캔의 초고속 연산 처리량과 성능은 거의 그대로 보존됨.
