# EPUB 페이지 넘김(Page-flip) 뷰어 도입 — 전체 작업 기록

> 이 문서는 `docs/plan_epub_windowed_pagination.md`(설계 결정 문서)의 자매 문서다. 그쪽이
> "무엇을 어떻게 하기로 했는가"에 집중한 설계 스펙이라면, 이 문서는 **어떻게 그 결론에
> 도달했는가** — 시작 지점, 조사 과정, 실제로 겪은 시행착오, 각 버그의 원인과 해결, 최종
> 결과, 그리고 앞으로 남은 작업까지 시간 순서대로 상세히 기록한 작업 일지다. 실전 구현에
> 들어가기 전에 반드시 §4(시행착오 상세 기록)를 먼저 읽을 것 — 여기 적힌 함정들은 실전
> 코드에서도 100% 재발할 수 있는 것들이다.

---

## 1. 배경과 목표

### 1-1. 출발점
만화(zip/cbz) 도서 전용으로 이미 성공적으로 파일럿을 마친 **page-flip(종이 넘김) 애니메이션
기능**(`docs/plan_page_turn_animation.md`, 2026-08-29 성공)이 있었다. 이 기능을 EPUB에도
적용해달라는 요청이 들어왔다 — "오른쪽의 '이 작가의 다른 도서'를 플러그인으로 분리해달라"는
별개 요청을 처리하던 중, 대화 말미에 이 요청이 나왔다.

### 1-2. 목표
- EPUB 본문에도 만화처럼 실제 종이가 넘어가는 듯한 2페이지 스프레드 애니메이션을 붙일 수 있는가?
- 가능하다면, 기존 프로덕션 뷰어 코드를 전혀 건드리지 않고 완전히 격리된 환경에서 기술적
  타당성부터 검증한다(만화 파일럿과 동일한 원칙).

---

## 2. 사전 조사 — "왜 이게 생각보다 어려운가"

### 2-1. 첫 번째 장벽: 현재 뷰어 구조가 근본적으로 안 맞음
현재 EPUB/TXT 뷰어(`static/js/viewer/txt_*.js`)는 CSS `column-width` + `column-count:auto` 다단
레이아웃에 가로 스크롤 스냅을 건 방식이다. "페이지"라는 게 실제로 분리된 DOM 조각이 아니라,
브라우저가 텍스트를 연속적으로 흘려 넣고 그 스크롤 위치 하나하나가 "페이지"인 셈이다.

반면 page-flip(St.PageFlip 라이브러리)은 `loadFromHTML()`에 **미리 분리된 페이지 DOM 배열**을
요구한다. 두 모델이 근본적으로 안 맞는다.

### 2-2. 두 번째 장벽: 업계 표준 라이브러리들도 같은 문제
epub.js와 그 후속격인 foliate-js(GNOME Foliate 리더의 렌더링 엔진)를 검토했는데, **둘 다
CSS 다단 + iframe 방식**이라 동일한 한계를 가지고 있었다. 즉 "연속 텍스트 → 분리된 페이지"로
바꿔주는 기존 해법이 없었다.

추가로, 이 프로젝트는 **과거에 epub.js를 실제로 쓰다가 버그(iframe·페이지 넘김 상호작용 문제
계열)로 인해 자체 엔진으로 갈아탄 전례**가 있다(`docs/epubjs_replacement_1/2/3_*.md`). page-flip
전용으로 좁혀서 epub.js를 재검토해봤지만, epub.js의 "paginated" 모드 역시 iframe+CSS컬럼
방식이라 이 특정 갭을 안 풀어주는 데다, 과거에 발목 잡았던 것과 같은 아키텍처를 다시 끌어들이는
셈이라 재도입 실익이 없다고 최종 판단, 기각했다.

### 2-3. 발견: Paged.js
**Paged.js**(MIT 라이선스, CSS Paged Media 스펙 폴리필, `pagedjs/pagedjs` 조직)가 유일하게
이 문제를 실제로 풀어주는 후보였다. 흘러가는 HTML 콘텐츠를 실측(측정) 기반으로 진짜 분리된
`<div class="pagedjs_page">` 박스들로 잘라준다 — 원래 인쇄/PDF 미리보기용으로 만들어진
라이브러리이지만, "연속 텍스트를 분리된 페이지 조각으로 자른다"는 핵심 기능은 정확히 우리가
필요로 하던 것이었다.

## 3. 테스트 환경 구축

기존 만화 page-flip 파일럿과 동일한 원칙 — **프로덕션 뷰어 코드는 절대 건드리지 않는다** —
을 그대로 따라 완전히 격리된 실험 라우트를 만들었다.

| 구성 요소 | 경로 |
|---|---|
| 라이브러리(신규 벤더링) | `static/lib/paged.polyfill.js` (Paged.js v0.4.3, MIT) |
| 라우트 | `api/routes/experimental_routes.py` — `/experimental/pagedjs-test` |
| 테스트 페이지 | `templates/experimental_pagedjs_test.html` (완전 독립, 인라인 CSS/JS) |
| 재사용한 기존 코드 | `services/text_epub_content_service.py`의 `get_epub_meta`/`get_epub_chapter`(읽기 전용) |

책 콘텐츠 소스로는 처음엔 `test/화산파 천재검귀`(실제 한글 웹소설 EPUB 9권, 텍스트 위주)를
썼고, 나중에 홈서버 실제 라이브러리 통계를 뽑은 뒤 `test/epub_size_bench`(최대/평균 크기 실물
EPUB 2권)를 추가했다. 둘 다 `.gitignore`의 `test/` 규칙으로 Git에는 커밋되지 않는다(저작권
있는 개인 라이브러리 콘텐츠이므로 의도된 것).

## 4. 시행착오 상세 기록 (시간 순서)

이 섹션이 이 문서의 핵심이다. 겪은 버그를 발생 순서 그대로, 원인과 해결까지 기록한다 — 실전
구현에서 똑같은 삽질을 반복하지 않기 위함이다.

### 4-1. Paged.js 자체 버그/함정

**① `auto:true` 기본값이 문서 자신을 페이지네이션 대상으로 삼음**
`paged.polyfill.js`는 로드되자마자(설정 없이 두면) `document.body` 전체를 자동으로
페이지네이션 대상으로 삼아 `wrapContent()`가 `body.innerHTML`을 통째로 비워버린다. 테스트
페이지의 컨트롤 UI가 로드 즉시 사라질 뻔했다.
→ **해결**: 스크립트 로드 전에 `window.PagedConfig = { auto: false }`를 먼저 설정하고, 버튼
클릭 시에만 수동으로 `new Paged.Previewer().preview(...)`를 호출.

**② `.pagedjs_page`를 미리 숨겨두면 렌더링 자체가 깨짐**
"보여줄 페이지 하나만 빼고 나머지는 `display:none`으로 숨겨두자"는 흔한 최적화를 시도했다가
`TypeError: Cannot read properties of null (reading 'getBoundingClientRect')` 크래시가 났다.
원인: Paged.js는 렌더링 도중 각 `.pagedjs_page`에 실제 콘텐츠를 채우며 오버플로를 실측하는데,
이 시점에 `display:none`이면 `offsetParent`가 `null`이 되어 내부 `Layout` 클래스의
`this.element.offsetParent.getBoundingClientRect()` 호출이 죽는다.
→ **해결**: CSS로 미리 숨기지 않고, 렌더링이 **완전히 끝난 뒤에만** JS에서 인라인
`style.display`로 페이지를 감춘다.

**③ `stylesheets=[]`를 넘기면 CSS(특히 `@page` 크기)가 통째로 무시됨**
`previewer.preview(content, stylesheets, renderTo)`에 빈 배열(`[]`)을 넘겼더니, `@page {
size: 420px 620px }`로 지정한 페이지 크기가 완전히 무시되고 Paged.js 기본값(8.5in × 11in,
96dpi 기준 816×1056px)으로 페이지가 만들어졌다. 원인: 빈 배열도 JS에서는 truthy라서
`if (!stylesheets) { stylesheets = this.removeStyles(); }` 폴백 분기를 안 타고,
`Polisher.add()`가 인자 없이 호출되어 CSS가 전혀 등록 안 됨. 이 버그 때문에 **한동안의 모든
페이지 수/속도 측정치가 실제로는 우리가 지정한 크기가 아니라 Paged.js 기본 크기 기준으로
나온 것**이었다(뒤늦게 `pages[0]` 실측 rect가 정확히 816×1056인 걸 발견하고서야 알아챔).
→ **해결**: CSS를 content 안 `<style>`이 아니라 `stylesheets` 인자에
`[{키: cssText}]` 형태(Paged.js `Polisher.add()`가 지원하는 "인라인 스타일시트" 포맷)로
직접 전달.

**④ `Polisher.setup()`이 만드는 `<style>`을 절대 스스로 안 지움 → 재계산할수록 느려짐**
`Polisher.setup()`은 `preview()`를 호출할 때마다 새 `<style>` 태그를 `document.head`에
추가하는데, 이걸 절대 스스로 안 지운다. 재계산(리사이즈 시뮬레이션) 시나리오에서 `new
Paged.Previewer()`를 매번 새로 만들면서 이전 인스턴스를 그냥 버리기만 했더니, head에
스타일시트가 계속 누적되면서 매 실행이 이전보다 느려지는 회귀가 발생했다 — 재계산이 최초
실행(9.08s)보다 **2배 이상 느린 20.6s**까지 나왔다.
→ **해결**: 새 `Previewer`를 만들기 전에 직전 `previewer.polisher.destroy()`(정확히
`styleEl.remove()`를 해줌)를 먼저 호출. 수정 후 같은 시나리오가 20.6s → 5.5s로 정상 범위
복귀 확인. **실전 구현에서 챕터 경계를 넘어 재페이지네이션할 때마다 이 정리를 빼먹으면, 오래
읽을수록(윈도우 재계산이 누적될수록) 점점 느려지는 회귀 버그가 그대로 재발한다.**

### 4-2. page-flip(St.PageFlip) 통합 버그/함정

**⑤ `size:'stretch'`를 쓰면 화면이 텅 비어 보임**
Paged.js 페이지는 이미 절대좌표 기반으로 픽셀 고정 레이아웃이 끝난 상태다. page-flip이 이
박스를 늘리거나 줄이면(`size:'stretch'`) 내부 콘텐츠는 원래 크기 그대로 남고 바깥 박스만
커져서 대부분 빈 공간만 남는다.
→ **해결**: `size:'fixed'`로 원본 픽셀 크기 그대로 표시.

**⑥ 페이지 엘리먼트가 `loadFromHTML()` 호출 이전에 이미 block의 직계 자식이어야 함**
St.PageFlip 공식 예제를 보면 페이지 `<div>`들이 `#book` 컨테이너(=`new PageFlip(container,
...)`에 넘긴 그 엘리먼트)의 직계 자식으로 미리 존재한 상태에서 `loadFromHTML()`을 호출한다.
우리는 `.pagedjs_page`를 별도 오프스크린 컨테이너(`#paged-target`)에 둔 채로 그대로
`loadFromHTML()`에 넘겼는데, 이게 원인일 거라 추정하고 미리 `bookEl`로 옮긴 뒤 재조회해서
넘기도록 고쳤다 — 그런데 이 수정만으로는 문제가 안 풀렸다(뒤에 나오는 ⑧이 진짜 원인).

**⑦ 진단 방법 자체의 맹점 — "표지가 원래 닫혀있는 것"과 "진짜 버그"를 구분 못함**
`.stf__item`(각 페이지 엘리먼트)의 상태를 확인하려고 `bookEl`에서 `firstElementChild`만
계속 따라 내려가며 로그를 찍었는데, 이 방식은 DOM 순서상 **항상 0번 페이지(표지)에만
도달**한다. `showCover:true`일 때 표지가 의도적으로 닫힌/숨김 상태인 것과 진짜 렌더링
버그를 구분하지 못해서 한동안 헛다리를 짚었다.
→ **교훈**: 유사한 시각화/가시성 디버깅 코드를 짤 때는 "첫 번째 것만 따라가며 보기"가 아니라
**전체 요소를 순회해서 스캔**하는 방식을 우선해야 한다. (`document.querySelectorAll('#flip-book
.stf__item')`을 전부 순회하며 `display !== 'none'`인 게 있는지 확인하는 방식으로 바꾸고서야
진짜 상태가 보이기 시작했다.)

**⑧ 진짜 원인: `.pagedjs_page`는 배경이 투명함**
구조/크기/위치는 로그상 전부 정상인데(x/y 좌표도 화면 안, `display:block`, 크기도 맞음) 화면엔
아무것도 안 보이는 상황이 계속됐다. 최종적으로 `getComputedStyle().backgroundColor`를
직접 찍어보고서야 밝혀짐: `.pagedjs_page` 자체는 배경이 없다(투명). 여태 흰 페이지로 보였던
건 `.pagedjs_page`가 원래 있던 컨테이너(`#paged-target`)에 `background:#fff`를 걸어뒀기
때문이었고, page-flip 쪽의 어두운 배경(`#flip-book`)으로 옮기고 나면 페이지가 투명해져서
검은 글씨가 어두운 배경 위에 있는 꼴이 되어 안 보였던 것이다. (`background: transparent`가
아니라 `rgba(0,0,0,0)`으로 표시돼서 자칫 "검은 배경"으로 오독하기 쉬웠던 것도 진단이 오래
걸린 이유 중 하나.)
→ **해결**: `#flip-book .pagedjs_page { background: #fff; }`를 명시적으로 지정.
→ **긍정적 재해석**: 배경이 자동으로 안 딸려온다는 건, 페이지 배경색/텍스트 색을 뷰어
테마(다크모드/세피아/e-paper 등)에 맞춰 우리가 명시적으로 통제할 수 있다는 뜻이다 —
실전 구현 시 테마 연동 지점으로 활용 가능.

**⑨ 스프레드 모드에서 `getCurrentPageIndex()`는 스프레드의 왼쪽 페이지만 대표 보고**
위치 복원(§4-4) 검증 중 발견. `turnToPage(12)`처럼 스프레드의 오른쪽 페이지 번호로 이동을
요청해도 정상적으로 그 스프레드(예: 11↔12페이지)가 표시되지만, `getCurrentPageIndex()`는
11을 반환한다. 버그가 아니라 St.PageFlip의 관례(스프레드를 대표하는 하나의 인덱스로 왼쪽
페이지를 쓰는 것)다.
→ **실전 적용 시 주의**: 위치 검증/저장 로직은 "현재 인덱스" 하나만 보지 말고, 스프레드
양쪽(idx, idx+1) 페이지를 모두 확인해서 실제로 보이는 텍스트 기준으로 로케이터를 계산해야
한다 — 왼쪽 페이지만 보고 저장하면 사용자가 실제로 읽고 있는(오른쪽에 보이는) 문단보다 앞선
위치가 저장될 수 있다.

### 4-3. 순수 라이브러리 자체 검증 (디버깅 전환점)

구조/스타일 버그가 겹겹이 쌓여 원인 추적이 막막해지자, **"발상의 전환"**으로 St.PageFlip
자체가 이 환경에서 정상 동작하는지부터 Paged.js 없이 순수 텍스트 3~5페이지(공식 예제와 동일한
구조: 표지 `data-density="hard"` + 일반 페이지들, block의 직계 자식으로 미리 존재)로 단독
검증했다. 이게 정상 작동해서(실제 2페이지 스프레드가 화면에 보임), 문제가 "라이브러리/환경
자체"가 아니라 "Paged.js가 만드는 복잡한 절대좌표 중첩 DOM 쪽"으로 범위가 좁혀졌다 — 그리고
그 답이 위 ⑧(투명 배경)이었다.

### 4-4. UI/UX 개선 시행착오

**⑩ 스크롤바 깜빡임으로 인한 화면 흔들림**
화면 전체를 book 무대로 채우도록(`position:fixed; inset:0;`) 바꾼 뒤, 페이지를 넘길 때마다
오른쪽에 스크롤바가 생겼다 사라지길 반복하며 화면이 흔들리는 문제가 생겼다. 원인: 넘김
애니메이션 중 페이지가 휘어지는 3D 변형이 컨테이너 경계를 순간적으로 살짝 벗어나면서
`overflow:auto`가 스크롤바를 만들었다 지웠다 했다.
→ **해결**: book 무대의 `overflow`를 `auto`가 아니라 `hidden`으로 고정(어차피 화면 크기에
맞춰 계산되어 정상적으로는 넘칠 일이 없음).

**⑪ 재계산 중 넘김 버튼이 안 잠겨서 오동작**
해상도를 바꿔가며 테스트하다가, 재계산이 내부적으로 진행 중인데도 넘김 버튼이 계속 눌려서
곧 destroy될 이전 `pageFlip` 인스턴스를 건드리며 오동작하는 게 확인됐다.
→ **해결**: 전체화면 로딩 오버레이(클릭 자체를 가로챔)로 재계산 중 상호작용을 원천 차단.
**이건 단순 UX 취향이 아니라 실측으로 드러난 진짜 버그를 막는 필수 조치였다** — 표시만
하는 로딩 UI로는 부족하고, 입력 자체를 막는 잠금이 있어야 한다는 게 확인됨.

**⑫ 챕터 경계마다 로딩이 튀어나와 거슬림 → 프리페치로 개선**
슬라이딩 윈도우(§4-5)를 "윈도우 끝에 정확히 도달한 순간"에만 재계산하도록 만들었더니, 챕터
경계를 넘을 때마다 로딩이 튀어나와 독서 흐름을 방해했다.
→ **해결**: 만화 뷰어의 스크롤 프리로드와 같은 원리로, **"끝나기 한 챕터 전"부터 미리
백그라운드에서 준비**하도록 개선. 무거운 Paged.js `preview()` 호출은 오프스크린
스테이징 영역(`#paged-target`, 원래도 화면 밖)에서 오버레이 없이 실행하고(`paginateOnly()`),
화면에 실제 영향을 주는 "바꿔치기"(destroy + loadFromHTML, 상대적으로 빠름) 구간만 짧게
로딩 오버레이로 감싼다(`swapInFlipBook()`). 준비하는 동안 사용자가 계속 페이지를 넘겼을
수 있으니, 바꿔치기 **직전 시점**의 실제 위치를 다시 읽어서 복원한다(프리페치 시작 시점
위치가 아니라).

### 4-5. 위치 보존(로케이터) 검증

각 문단(`p`, `div`)에 `data-loc="ch{챕터idx}-p{문단idx}"` 마커를 심어서, 재계산 전후로
같은 텍스트 위치를 다시 찾아갈 수 있는지 검증했다.

**첫 시도 실패**: 챕터 래퍼(`<section>`) 자체에도 `data-loc="ch4-title"`을 달아뒀더니, DOM
순서상 조상이 자손보다 먼저 나와서 `page.querySelector('[data-loc]')`가 항상 이 래퍼(제목)만
찾아버리고 실제 문단(`ch4-p5` 등)까지 못 내려가는 문제가 있었다 — 재계산 후 항상 챕터 맨
앞으로 튕겨나가는 것처럼 보였다.
→ **해결**: 챕터 래퍼에는 `data-loc`을 안 달고, `<h2>`(제목)에만 별도로 달아서 "챕터 첫
페이지로 이동"과 "특정 문단으로 이동"을 구분되게 함.

검증 결과: 페이지 번호/총 페이지 수가 재계산 전후로 완전히 달라져도(예: 443페이지 →
407페이지) 같은 문단으로 정확히 복원되는 것을 확인했다. (§4-2 ⑨의 스프레드 왼쪽/오른쪽 이슈도
이 검증 과정에서 함께 발견됨.)

### 4-6. 슬라이딩 윈도우 구현 → 최종 폐기(기본값에서)

§3(설계 방향)의 핵심 아키텍처 — 윈도우가 챕터 경계를 넘으면 앞/뒤를 편입하고 오래된 챕터는
폐기 — 를 실제로 구현했다. 챕터별 fetch/캐싱, 윈도우 범위(`[start, end]`) 관리, 크기 초과 시
폐기, §4-4 ⑫의 프리페치 개선, §4-5의 위치 복원까지 전부 정상 동작을 확인했다.

**그런데 실사용 비교에서 뒤집힘**: 슬라이딩 윈도우 없이 그냥 처음부터 끝까지 통째로 로드해서
읽어본 결과, 프리페치로 로딩을 최소화한 윈도우 방식보다도 "통째로가 더 깔끔하다"는 평가가
나왔다. 이후 실제 홈서버 EPUB 크기 분포를 조사해본 결과와 종합해서(§5), **기본 동작을 통째
로드로, 초대형 파일만 별도 제약으로 처리**하는 쪽으로 최종 결론이 났다(§6 참고). 슬라이딩
윈도우 구현 자체는 삭제하지 않고 남겨뒀다 — 검증된 대안이라 나중에 필요해지면 바로 꺼내 쓸
수 있다.

## 5. 실제 라이브러리 규모 조사 (홈서버 MariaDB)

"통째로 로드"가 실전에서 안전한 선택인지 판단하려고 실제 데이터를 조회했다.

**쿼리 대상**: 홈서버(`192.168.0.20:3306`) MariaDB `media_general.books`, `file_format='epub'`,
삭제되지 않은 항목. (성인 라이브러리(`media_adult`)엔 EPUB 0권.)

**총 107,162권** (0바이트 깨진 파일 94개 제외 후 107,068권 기준):

| 지표 | 값 |
|---|---|
| 최소 | 47.5KB |
| 중앙값(p50) | 1.1MB |
| **평균** | **7.68MB** |
| p75 | 6.92MB |
| p90 | 22.77MB |
| p95 | 34.31MB |
| p99 | 69.15MB |
| **최대** | **496.5MB** |

100MB 초과 381권, 50MB 초과 2,828권, **200MB 초과는 39권(0.036%)**. 상위권을 직접 확인해보니
오분류가 아니라 **요리책/엑셀·디자인 튜토리얼처럼 이미지가 잔뜩 박힌 실용서**들이었다(예:
"행복한 집밥 삼시세끼" 477MB, "무작정 따라하기 엑셀&파워포인트&워드" 365MB).

이 조사 결과를 바탕으로, 최대 파일(496.5MB)과 평균에 가장 가까운 파일(7.7MB, "내 인생이다
임마" #98)을 홈서버에서 SFTP로 내려받아(`test/epub_size_bench/`, Git 미커밋)
극단값 벤치마크를 진행했다.

### 5-1. 극단값 실측 — 이미지 로딩 비용 포함

처음엔 이미지가 전부 깨져 보였다. 챕터 HTML의 `<img>` 태그가 프로덕션 엔드포인트
(`/api/media/epub-image?book_id=...`)를 가리키는데, 테스트 파일들은 DB에 등록된 book이
아니라서 `book_id=None`으로 항상 404였다 — **실제 이미지 로딩/디코딩 비용이 그동안의 모든
측정에서 통째로 빠져 있었다**는 뜻이다(사용자가 직접 화면을 보고 지적해서 발견).

→ **해결**: 테스트 전용 이미지 서빙 라우트(`/experimental/pagedjs-test/api/epub-image`,
book_id 없이 파일 경로를 직접 해석)를 추가하고, 프론트에서 챕터 HTML을 받아올 때
`<img src="...book_id=None...">`를 이 라우트로 정규식 치환하도록 고쳤다.

**재실측 결과** (496.5MB EPUB, 50챕터, 페이지 573×845px, 글자크기 12px, 이미지 포함):

| 지표 | 값 |
|---|---|
| 챕터 fetch(이미지 포함) | 3,416ms |
| 페이지네이션(최초 실행) | 3,358ms |
| 결과 페이지 수 | 94 |

로컬 디스크 기준 이미지 포함 극단값이 약 **3.4초 + 3.4초** 수준 — 원격(GDrive/rclone) 환경에서
지연이 10배 늘어나도 감수할 만한 속도라는 게 최종 판단.

## 6. 최종 결정사항 요약

`docs/plan_epub_windowed_pagination.md` §4에 상세 기록되어 있으며, 여기서는 핵심만 요약한다.

1. **적용 범위**: EPUB만. TXT는 챕터 구조가 없어 위치 로케이터를 안정적으로 만들 수 없어 제외.
2. **윈도우 크기 / 로딩 전략**: ~~슬라이딩 윈도우~~ → **최종: 기본은 책 전체를 한 번에 로드.**
   **EPUB 파일 크기가 200MB를 넘으면 page-flip 모드 자체를 지원하지 않는다** (홈서버 실측 기준
   39/107,068권=0.036%만 해당, 영향 미미). 슬라이딩 윈도우 구현은 폐기하지 않고 검증된
   대안으로 보관.
3. **재계산 트리거**: release 시점(`change` 이벤트)에만 재계산. 드래그 중 debounce는 채택 안 함
   (재계산 자체가 debounce 주기보다 오래 걸릴 수 있어 요청이 밀리는 문제 우려).
4. **재계산 중 UX**: 전체화면 로딩 오버레이로 입력 자체를 차단 (§4-4 ⑪에서 확인된 실제 버그를
   막는 필수 조치, 단순 표시용 UI 아님).
5. **위치 보존 방식**: 챕터 idx + 챕터 내 오프셋(문단 단위로 근사 검증, 실전에서는 문자
   오프셋까지 정밀화 가능). 페이지 인덱스는 재계산마다 의미가 바뀌므로 저장 기준으로 못 씀.
6. **page-flip 연동 시점**: 로딩/재계산 완료 후, 실제 페이지를 넘기는 상호작용부터 개입. 로딩
   자체는 page-flip과 무관하게 별도 로딩 표시로 처리.
7. **모바일 지원 범위**: 휴대폰 미지원, 아이패드급 태블릿 해상도부터 지원 (User-Agent가 아니라
   화면 폭 기준 게이팅, 만화 파일럿의 `usePortrait`/`minWidth` 방식과 동일).

## 7. 검증된 것 vs 아직 안 된 것

### ✅ 검증 완료 (오늘 실측/재현됨)
- Paged.js가 실제 한글 텍스트(이미지 포함)를 페이지 단위로 정확히 잘라내는가
- page-flip 2페이지 스프레드 + 곡률 애니메이션이 실제로 붙는가
- 재계산(폰트 변경) 성능이 쓸 만한 범위인가 (스타일 누적 버그 수정 포함)
- 페이지 번호가 바뀌어도 텍스트 위치를 복원할 수 있는가
- 재계산 중 상호작용을 막아야 하는 실제 필요성
- 슬라이딩 윈도우 + 챕터 경계 프리페치가 기술적으로 동작하는가
- 홈서버 실제 EPUB 크기 분포, 극단값(496.5MB, 이미지 포함) 성능

### ⬜ 아직 검증 안 됨 (실전 구현 착수 전 확인 권장)
- **태블릿 해상도 게이팅의 정확한 breakpoint 값** — 결정은 됐으나 실측 안 됨
- **GDrive/rclone 원격 스토리지 환경에서의 실제 배수** — 로컬 극단값(3.4s+3.4s) 기준 "10배까지는
  감수 가능"이라는 게 사용자의 잠정 판단이었을 뿐, 실제 원격 배수 실측은 아직 없음
  (`project_gdrive_rclone_majority_userbase` 메모 참고 — 이 프로젝트 사용자 대다수가
  rclone 마운트 GDrive를 쓰므로 반드시 확인 필요)
- **평균 크기(7.7MB) EPUB의 실측** — 다운로드는 해뒀지만(`test/epub_size_bench/`) 아직 이
  파일로는 테스트를 안 돌려봄
- **재계산 디바운스(release 정책)의 실사용 시나리오 검증** — 정책만 정했지 실제 폰트 크기
  슬라이더 드래그 시나리오로 테스트 안 됨
- **200MB 초과 EPUB의 대체 UX** — "page-flip 미지원"이라고만 정했지, 그럴 때 정확히 어떤
  화면/안내를 보여줄지는 미정 (기존 스크롤형 뷰어로 자동 폴백? 안내 메시지? 등)
- **위치 로케이터의 문자 단위 정밀화** — 지금은 문단 단위 근사로만 검증됨. 실전에서는 한
  문단이 여러 페이지에 걸쳐 쪼개질 때 정확히 어느 지점인지까지 필요할 수 있음
- **프로덕션 `epub_session`(CFI/href/index/percent) 스키마와의 통합 방식** — 새 필드를
  추가할지, 기존 스키마를 확장할지 미정

## 8. 앞으로 남은 작업 (실전 구현 로드맵)

1. **위 §7의 미검증 항목부터 처리** — 특히 GDrive 원격 지연 실측은 사용자 대다수가 영향받는
   부분이라 우선순위가 높음.
2. **200MB 제한 로직을 어디에 둘지 설계** — 스캔 시점에 파일 크기를 판단해 플래그를 미리
   저장해둘지, 뷰어 진입 시점에 그때그때 확인할지 결정.
3. **윈도우 방식 구현을 실전 코드로 이식하지 않고 보류** — 200MB 이하는 통째 로드로 충분하다는
   결론이므로, 당장은 슬라이딩 윈도우 로직을 실전에 옮길 필요가 없다. `/experimental/pagedjs-test`의
   구현을 참고 자료로만 남겨둔다.
4. **프로덕션 EPUB 뷰어에 "page-flip 모드" 진입점 추가** — 기존 스크롤/2단 컬럼 모드와 나란히
   둘지, 완전 대체할지는 별도 결정 필요 (사용자 확인 없이 임의로 정하지 말 것 — 기존
   `plan_page_turn_animation.md` §5-1 원칙과 동일하게 적용).
5. **위치 로케이터를 실제 진행률 저장(`epub_session`)과 연동**하는 설계/구현.
6. **모바일/태블릿 breakpoint 실측 후 반영**.
7. **평균 크기 EPUB(`test/epub_size_bench`에 이미 준비됨)로 마저 실측**해서 "일반적인 케이스"
   기준 숫자도 확보.
8. 위 항목들이 어느 정도 정리되면 **실제 프로덕션 뷰어 코드(`static/js/viewer/txt_*.js` 등)에
   통합** — 이 시점부터는 "완전 격리된 실험"이 아니라 진짜 기능 개발이므로, 착수 전 반드시
   사용자와 통합 방식(§4 항목 4 참고)을 재확인할 것.
