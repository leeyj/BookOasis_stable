# EPUB 페이지네이션 엔진 — 윈도우 구조 설계 (초안)

> 상태: **설계 결정 + 스파이크 검증 전부 완료(2026-09-06), 실전 구현 착수 대기.** §4의 결정 항목
> 전부 확정됨(윈도우 크기 항목은 당일 오후 최종적으로 뒤집혀 "기본은 통째 로드 + 200MB 초과 시
> page-flip 미지원"으로 확정). §5의 성능/버그 항목들도 실측 검증까지 마침 — 이제 남은 건 실전 코드에
> 옮기는 것뿐. `plan_page_turn_animation.md`(만화 page-flip 파일럿)의 후속 — "이걸 EPUB/TXT에도
> 적용할 수 있나?"에서 출발한 조사/스파이크 테스트 결과를 반영한다.
> **범위: EPUB만.** TXT는 챕터 구조가 없어 청크 경계를 안정적인 위치 로케이터로 쓰기 어렵고
> (진행률 저장/복원이 어려워짐) 제외했다 (2026-09-06 결정, §4 참고).

## 1. 여기까지 오게 된 경위 (요약)

1. 만화(zip/cbz)용 page-flip 페이지 넘김 애니메이션 파일럿(`plan_page_turn_animation.md`)이 성공한 뒤,
   같은 걸 EPUB/TXT에도 적용해달라는 요청을 검토.
2. 현재 EPUB/TXT 뷰어(`static/js/viewer/txt_*.js`)는 CSS `column-width` + 스크롤 스냅 방식 — page-flip이
   요구하는 "미리 분리된 페이지 DOM 배열"을 만들어주지 않음이 확인됨.
3. epub.js / foliate-js도 동일하게 iframe+CSS컬럼 방식이라 이 갭을 안 풀어줌. 과거 이 프로젝트가
   epub.js를 버그(iframe·페이지 넘김 상호작용 문제 계열)로 인해 자체 엔진으로 갈아탄 전례도 있어
   재도입 실익 없다고 판단, 기각.
4. **Paged.js**(MIT, CSS Paged Media 폴리필)가 유일하게 "흘러가는 HTML → 실측 기반 분리된 페이지 박스"를
   만들어주는 후보로 확인됨.
5. 코어를 건드리지 않고 `/experimental/pagedjs-test` 격리 라우트로 스파이크 테스트 진행
   (`test/화산파 천재검귀/*.epub` 9권 대상, 실제 웹소설 EPUB).

## 2. 실측 결과

| 조건 | 챕터 fetch | 페이지네이션 | 결과 페이지 수 | 페이지당 비용(역산) |
| :--- | :--- | :--- | :--- | :--- |
| 10챕터, 스로틀 없음 | 37ms | 565ms (최초) / 553ms (재계산) | 78 | ~7.2ms |
| 28챕터(1권 전체), CPU 4× 스로틀 | 414ms | 9,081ms (최초) | 348 | ~26ms |
| 28챕터(1권 전체), CPU 4× 스로틀 | - | **20,599ms (재계산)** | 348 | ~59ms |

관찰:
- 페이지 수 대비 비용은 대략 선형(스로틀 배수와 얼추 비례) — 문서가 커질수록 제곱 이상으로
  폭발하는 징후는 이 범위(78~348페이지) 안에서는 뚜렷하지 않음.
- 그러나 **재계산(같은 콘텐츈 재페이지네이션)이 최초 실행보다 오히려 더 느림** (9.08s → 20.6s,
  28챕터/4× 스로틀 기준) — 이전 실행의 DOM/메모리가 완전히 정리되지 않고 누적되는 것으로 추정됨
  (원인 미확정, §5-2 참고).
- **결론**: "책 한 권을 통째로 미리 페이지네이션"하는 모델은 기각. 폰트/리사이즈 재계산이 반복되는
  실사용 패턴에서는 특히 치명적(20초는 논외 수준).

## 3. 채택 방향: 윈도우(Windowed) 페이지네이션

전체 책이 아니라 **현재 읽는 위치 주변 콘텐츠만** Paged.js로 페이지네이션하고, 사용자가 윈도우
경계에 다다르면 앞/뒤 챕터를 편입해 재계산한다. 윈도우 크기는 고정 챕터 수가 아니라 만화 뷰어처럼
"화면을 채우고도 여유 버퍼가 남는 만큼" 동적으로 유지하는 방식으로 확정됨 (§4 참고).

- 기존 EPUB 뷰어가 이미 챕터 단위 지연로딩 + 배치 프리페치(`get_epub_chapters_batch`,
  `project_epub_batch_prefetch_fix` 메모 참고)를 쓰고 있으므로, 윈도우 관리 로직은 이 기존 인프라
  위에 얹는 게 자연스럽다 — 새로 만들 필요 없음.
- 10챕터/565ms 데이터가 참고 기준선이 되긴 하지만, 정확한 버퍼 크기별 재계산 비용은 §5-3에서
  스타일 누적 버그를 고친 뒤 재실측해야 신뢰할 수 있다.

## 5. 기술적으로 추가 확인 필요한 것

- **§5-1 재계산이 최초 실행보다 느린 원인 — 규명 완료, 테스트 하네스에 수정 반영함.**
  `Polisher.setup()`(Paged.js 내부, `static/lib/paged.polyfill.js` 27498줄)이 `preview()`를 호출할
  때마다 새 `<style>` 태그를 `document.head`에 추가하는데, 이걸 스스로 절대 안 지운다. `new
  Paged.Previewer()`를 매 실행마다 새로 만드는 테스트 코드에서 이전 인스턴스를 그냥 버리기만 했더니
  head에 스타일시트가 계속 쌓이면서 매 실행이 이전보다 느려졌던 것 — 재계산이 최초 실행보다
  2배 이상 느렸던(9.08s → 20.6s) 원인이 이것.
  **수정**: 새 Previewer를 만들기 전에 직전 Previewer의 `polisher.destroy()`(정확히
  `styleEl.remove()`를 해줌)를 먼저 호출하도록 `experimental_pagedjs_test.html`에 반영함. **실전 윈도우
  구현에서도 챕터 경계를 넘어 재페이지네이션할 때마다 이 정리를 반드시 해야 하며, 안 하면 오래
  읽을수록(윈도우 재계산이 누적될수록) 점점 느려지는 회귀 버그가 된다 — 설계에 명시적으로 넣을 것.**
  **재검증 완료(2026-09-06)**: 수정 후 같은 28챕터(전체 1권) 재계산이 20.6s → 5.5s(글자크기 13px,
  246페이지 기준)로 정상 범위 복귀 확인. 단, 이 숫자는 여전히 "책 한 권 전체 재계산"이라는 이미
  기각된 시나리오 기준이라 참고용일 뿐 — 실제 채택한 동적 버퍼 윈도우 방식에서는 재계산 대상 분량이
  훨씬 작으므로 체감 비용은 이보다 낮을 것으로 예상. 정확한 수치는 §5-3(윈도우 크기별 실측)에서 확인.
- 윈도우 크기별(1/2/3/5챕터) 재계산 비용을 실측해 "체감 가능한 최대 윈도우"를 구체적으로 찾을 것.
- 챕터 경계를 넘을 때 "윈도우를 앞으로 민다"의 정확한 정책 (예: 항상 현재 챕터 ±1 유지 vs 다 읽은
  뒷챕터는 버리고 새 챕터만 추가).
- GDrive/rclone 원격 스토리지 환경에서 챕터 fetch 자체의 지연 (이번 로컬 테스트는 로컬 디스크 기준).

## 5-4. page-flip(St.PageFlip) 연동 — 실제로 됨 확인(2026-09-06), 발견한 함정들

`/experimental/pagedjs-test`에 Paged.js가 만든 `.pagedjs_page`를 St.PageFlip의 `loadFromHTML()`에
직접 연결해서, 2페이지 스프레드 + 실제 종이 곡률 애니메이션까지 정상 동작하는 걸 확인했다(한글 웹소설
본문으로 실측). §4에서 결정한 "로딩 후 페이지 넘길 때부터 page-flip 개입"이 기술적으로 가능함이
증명됨. 다만 붙이는 과정에서 순서대로 4개의 함정에 걸렸고, 전부 실전 구현에도 그대로 적용된다:

1. **`size:'stretch'` 쓰면 안 됨.** Paged.js 페이지는 이미 절대좌표 기반으로 픽셀 고정 레이아웃이
   끝난 상태라, page-flip이 그 박스를 늘리거나 줄이면 내부 콘텐츠는 원래 크기 그대로 남고 바깥
   박스만 커져서 대부분 빈 공간만 남는다. 반드시 `size:'fixed'`로 원본 픽셀 크기 그대로 표시해야
   한다.
2. **`preview(content, stylesheets, renderTo)`에 빈 배열(`[]`)을 넘기면 CSS가 통째로 무시된다.**
   빈 배열도 JS에서는 truthy라 "stylesheets 없음" 폴백 분기(`removeStyles()` 호출)를 안 타는데, 그
   결과 `Polisher.add()`가 인자 없이 호출되어 `<style>` 안에 넣어둔 `@page` 크기 지정이 전부
   무시되고 Paged.js 기본값(8.5in x 11in, 816x1056px)으로 페이지가 만들어진다. CSS(특히 `@page`
   크기)는 반드시 `stylesheets` 인자에 `[{키: cssText}]` 형태로 직접 넘겨야 한다.
3. **St.PageFlip도 컨테이너가 `display:none`인 상태로 초기화하면 안 됨.** Paged.js와 같은 부류의
   `getBoundingClientRect` 오류. 컨테이너를 먼저 보이게 한 뒤 `new St.PageFlip(...)`을 호출해야 한다.
4. **`.pagedjs_page`는 배경이 투명하다.** 지금까지 흰 페이지로 보였던 건 `.pagedjs_page` 자체가
   흰 배경이어서가 아니라, 원래 있던 컨테이너(`#paged-target`)에 `background:#fff`를 걸어뒀기
   때문이었다. page-flip 쪽 컨테이너로 옮기고 나면 페이지가 투명해져 어두운 배경 위에서 검은
   글씨가 안 보이는 것처럼 보인다(구조/크기/위치는 전부 정상이라 진단이 오래 걸렸음). **오히려
   긍정적으로 보면**: 배경이 자동으로 안 딸려오므로, 뷰어 테마(다크모드/세피아/e-paper 등)에 맞춰
   페이지 배경색과 텍스트 색을 우리가 명시적으로 통제할 수 있다는 뜻 — 실전 구현 시 테마 연동
   지점으로 활용.

원인 진단 과정에서 St.PageFlip 자체가 이 환경에서 정상 동작하는지 먼저 순수 텍스트 3페이지(공식
예제와 동일 구조)로 단독 검증했고(정상 작동 확인), 이후 "전체 `.stf__item`을 순회해서 display가
none이 아닌 게 있는지" 직접 스캔하는 방식으로 좁혀나갔다 — 첫 번째 접근(DOM 트리를 `firstElementChild`만
따라 내려가며 로그)은 항상 0번 페이지(표지, `showCover:true`일 때 의도적으로 닫힌 상태)에만 도달해서
"진짜 버그"와 "정상적으로 닫힌 표지"를 구분 못하는 맹점이 있었다는 것도 교훈 — 유사한 진단 코드를
다시 짤 때는 전체 요소를 스캔하는 방식을 우선할 것.

## 5-5. 위치 보존(§4 결정) — 재계산을 버텨내는지 검증 완료(2026-09-06)

§4에서 로케이터를 "챕터 idx + 챕터 내 오프셋"으로 정한 게 실제로 유효한지 실측했다. 방법: 각 문단
(`p`, `div`)에 `data-loc="ch{챕터idx}-p{문단idx}"`를 심어두고, 재계산(폰트 크기 변경) **직전**
현재 페이지의 로케이터를 기록 → 재계산 **후** 그 로케이터를 포함한 페이지를 다시 찾아 `turnToPage()`로
이동. 페이지 번호/총 페이지 수가 재계산 전후로 완전히 달라졌음에도(예: 443페이지 → 407페이지) 같은
문단으로 정확히 복원됨을 확인했다.

**부수적으로 확인된 St.PageFlip API 특성** (실전 구현 시 알아둘 것): 2페이지 스프레드 모드에서
`getCurrentPageIndex()`는 현재 스프레드의 **왼쪽 페이지 인덱스만** 대표로 보고한다. `turnToPage(12)`처럼
스프레드의 오른쪽 페이지 번호로 이동을 요청해도 정상적으로 그 스프레드(예: 11↔12페이지)가 표시되지만,
`getCurrentPageIndex()`는 11을 반환한다 — 버그가 아니라 관례. **위치 검증/저장 로직을 실전에 옮길 때는
"현재 인덱스" 하나만 보지 말고, 스프레드 양쪽(idx, idx+1) 페이지를 모두 확인해서 실제로 보이는 텍스트
기준으로 로케이터를 계산해야 한다** — 왼쪽 페이지만 보고 저장하면 사용자가 실제로 읽고 있는(오른쪽에
보이는) 문단보다 앞선 위치가 저장될 수 있다.

## 5-6. 재계산 중 상호작용 차단 — 실사용 버그로 확인, 오버레이로 해결(2026-09-06)

해상도를 바꿔가며 테스트하다가, 재계산이 내부적으로 진행 중인데도 넘김 버튼이 계속 눌려서 곧
destroy될 이전 `pageFlip` 인스턴스를 건드리며 오동작하는 게 확인됨. 전체화면 로딩 오버레이(클릭
자체를 가로챔)로 재계산 중 상호작용을 원천 차단해서 해결. **§4의 "재계산 중 UX = 로딩 표시" 결정은
단순 UX 취향이 아니라 이 실측 버그를 막는 필수 안전장치였음이 확인됨 — 실전 구현에서도 표시만 하는
로딩 UI가 아니라 입력 자체를 막는 잠금이 있어야 한다.**

## 5-7. 슬라이딩 윈도우 + 챕터 경계 프리페치 — 스파이크 구현 및 검증 완료(2026-09-06)

§3의 핵심 아키텍처(윈도우가 챕터 경계를 넘으면 앞/뒤를 편입하고 오래된 챕터는 폐기)를
`/experimental/pagedjs-test`에 실제로 구현해 검증함:

- 챕터 하나씩 fetch/캐싱, 윈도우 범위(`[start, end]`) 관리, 크기 초과 시 반대쪽 챕터 폐기 로직이
  정상 동작.
- 재계산 후 §5-5의 로케이터 복원 메커니즘으로 위치 유지 확인.
- **1차 구현은 "윈도우 끝에 정확히 도달한 순간"에만 재계산을 걸어서 챕터 경계마다 로딩이 튀어나와
  거슬린다는 피드백 발생** → 만화 뷰어의 스크롤 프리로드와 같은 원리로 **"끝나기 한 챕터 전"부터
  백그라운드로 미리 준비**하도록 개선. 무거운 Paged.js `preview()` 호출은 오프스크린 스테이징
  영역(`#paged-target`)에서 오버레이 없이 실행하고, 화면에 실제 영향을 주는 "바꿔치기"(destroy +
  loadFromHTML) 구간만 짧게 로딩 오버레이로 감싼다 (`paginateOnly()` / `swapInFlipBook()` 분리).
  준비하는 동안 사용자가 계속 페이지를 넘겼을 수 있으니, 바꿔치기 직전 시점에 위치를 다시 읽어서
  복원한다(프리페치 시작 시점 위치가 아니라).
- **최종 실사용 비교 피드백**: 실제로 처음부터 끝까지 넘겨보니 "윈도우 없이 통째로 로드"가 더
  깔끔하게 느껴졌다는 평가 — 단, 이건 §5-7 하단의 실제 EPUB 크기 분포 데이터를 함께 봐야 한다
  (텍스트 위주 도서엔 통째 로드가 문제없지만, 이미지 많은 도서는 다를 수 있음).
